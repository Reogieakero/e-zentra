01 · Pipeline

How a request flows through the API

Every call passes through the same layered pipeline. Middleware authenticates and authorizes, Zod rejects anything unexpected, the service owns the domain rules, and the error handler normalizes every failure.

1 · Rate limiter
Fixed-window counter in Upstash Redis via INCR + PEXPIRE. Global 100 req/min/IP; auth endpoints 5 req/min/IP. No Lua EVAL, no KEYS — fully Upstash-compatible.
▼
2 · Authenticate
Reads Authorization: Bearer <jwt>, verifies the access token (HMAC), loads the user, and requires accountStatus = active.
▼
3 · Authorize
requireRole(...) checks the role allowlist; grade-band ownership (Record Keeper = JHS 7–10, Registrar = SHS 11–12) is enforced at the service layer for every write.
▼
4 · Validate
validateSchema parses params / query / body with Zod, using .strict() so unknown fields are rejected with 422.
▼
5 · Service
Domain logic runs here: Prisma queries, Redis cache/rate keys, business invariants, notifications, and audit-log writes. Transactions guarantee atomicity (e.g. bulk grade components).
▼
6 · Serialize
serializeForOutput converts Date → ISO string and Prisma.Decimal → number; responses are wrapped as { data, page, pageSize, total, hasMore }.
▼
7 · Respond / Error
Success returns 2xx. Failures are mapped by errorHandler: ApiError status codes, Prisma known-request errors, Multer errors, then a safe 500 fallback (see the error table below).
Why this matters: the pipeline guarantees that invalid input never reaches a service, that every mutation is audited, and that a client always receives a structured { error: { code, message } } envelope instead of a raw exception.

02 · Identity

Auth, sessions & grade-band ownership

Accounts register as pending and must be approved by the correct grade-band owner. Sessions use a short-lived access token plus a rotated, hashed, revocable refresh token.

Registration → approval workflow

Self-register
POST /auth/register/student|parent|teacher creates the account with pending status.
Band owner approves
POST /users/:id/approve. Wrong owner → 403. Approving a student also auto-confirms their pending parent link.
Login
POST /auth/login (argon2 verify) issues an access token (15m) and a refresh token stored as an argon2 hash.
Rotate / revoke
Each POST /auth/refresh rotates the token (old one is revoked, reuse → 401). Logout and password change revoke everything.

Login hardening: 5 failed attempts per account locks login for 15 minutes. Tokens are never stored raw — refresh tokens are argon2-hashed so a DB leak can't be replayed.

Row identity

One record per student · day · session

Enforced by the DB unique index (studentId, attendanceDate, session). A student can't be double-marked for the same morning or afternoon; re-sending a roster just skips the existing rows.

Statuses

Four values

present · absent · late · excused. Only present counts toward the present-rate consumed by risk detection — everything else lowers it.

Risk feed

Present-rate < 80% ⇒ signal

After every mark and every edit, recomputeRiskAndNotify re-runs the three-signal scan. Poor attendance is the most common path into moderate/high risk.

Side effects per write: every absent/late row emits an attendance_alert to all confirmed parents (notifyParentsOfStudent), the student's risk assessment is upserted, and one audit entry records the batch (CREATE on the section, UPDATE per corrected row).

05 · Grades

The grading engine & DepEd transmutation

Grades are computed server-side with a fully transparent, testable pipeline — from weighted component averages to the official DepEd DO 8, s. 2015 transmutation table.

1
Components
Bulk set for subject/term; weights must sum to 100
→
2
Assessments
Teacher defines quiz / performance task / exam
→
3
Scores
Per-student scores, editable until lock
→
4
Compute
Initial grade → transmuted → remarks; triggers risk recompute
→
5
Finalize / Lock
Lock freezes grades → further edits return 409

Component average

Per component type

Average of (score ÷ maxScore) × 100 across all assessments of that type. Missing scores are excluded.

Initial grade

Weighted blend

Σ(average × weight) ÷ Σ(weight) over the three components. A missing component marks the grade incomplete.

Transmuted grade

DepEd DO 8, s. 2015

Maps the initial grade through the official transmutation table. 75–100 stay as-is; 0–74 compress into a 60–74 band. Passing = transmuted ≥ 75.

06 · Oversight

Risk detection logic

Risk is a transparent, rule-based counter — deliberately not a black-box ML score, so every classification can be explained to teachers and parents. Computed per student per term.

Academicrisk_count +1
Average of the term's transmuted final grades is below 75. Only evaluated when at least one final grade exists.
Attendancerisk_count +1
Present-rate (present ÷ total records) drops below 80%. Only evaluated when at least one attendance record exists.
Behavioralrisk_count +1
At least one anecdotal record filed for the term — a flag on behavior, health, or home context.
Signals trueRisk level
0low
1moderate
2+high

When it runs

computeRiskSignals pulls final grades, attendance records, and anecdotal counts in parallel, then upserts the result into student_risk_assessments (per student + term).

It is recomputed automatically whenever a final grade is computed, or on demand via POST /risk-assessments/assess (staff only).

When the level changes and risk is ≥ 1, the student (and optionally parents) receive an at_risk_flagged notification.

Design note: all three signals missing data ⇒ risk stays low. If it later moved to a weighted ML score, the API contract, storage fields, and notifications would stay the same — only the internal engine would change.

07 · Flags

Record flags & auto-escalation

Any staff member can flag a sensitive record for review. Flags can be resolved, escalated manually, or escalated automatically by the background job when they go stale.

Manual flow

Flag a record
POST /record-flags — staff link a record to a reason (sourceTable + sourceRecordId + flagReason); band owners are notified.
Resolve
POST /record-flags/:id/resolve sets status resolved.
Manual escalate
POST /record-flags/:id/escalate marks escalatedToPrincipal and notifies all principals.

Auto-escalation job

src/jobs/flagEscalation.ts runs on boot and then every 60 seconds:

Scan stale flags
Open, not-yet-escalated flags older than RECORD_FLAG_ESCALATION_DAYS (default 7).
Escalate + notify
Sets escalatedToPrincipal + escalatedAt, then notifies every principal via record_flag_escalated.
Guard
Job is no-op unless RECORD_FLAG_ESCALATION_ENABLED=true; interval is unref() so it never blocks shutdown.

Verified end-to-end by an integration test that seeds a 30-day-old flag and asserts escalation + principal notification.

Guarantees

Duplicates are rejected with 409 (unique parentId + studentId). Only pending_confirmation links can be resolved. A parent can only confirm their own link; other roles are restricted by the staff allowlist. Every resolution writes an audit entry and notifies both sides.

11 · Inbox

Notifications & audit trail

Two cross-cutting systems keep every stakeholder in the loop and every change provable: a per-user notification inbox with fan-out to confirmed parents, and an immutable audit log. Both are written synchronously inside the same service call that triggers them.

Fan-out helpers

One row per recipient, written per call

notify()
Creates a single notification row. Best-effort: any failure is caught and logged — a notification problem can never fail the operation that caused it.
notifyStudentAndParents()
Notifies the student, then every parent with a confirmed link (skip parents via a flag). Used for grades, risk flags, and report cards.
notifyParentsOfStudent()
Parents only — used for attendance alerts, where the student already knows the fact in person.
getConfirmedParentsOfStudent()
Resolves the parent fan-out list from parent_student_links (status confirmed) at write time.

Audit trail

Immutable journal

Every state-changing operation calls writeAudit with actorId · action · tableName · recordId, plus JSON oldValue/newValue snapshots of the row. Entries are append-only — never updated, never deleted.

It answers who changed what, when, and to what value — the trail required for DepEd record-keeping and incident review.

Delivery semantics

Best-effort, in-process: rows are written synchronously in the same call; individual failures are caught and logged, so a notification hiccup can't roll back the underlying mutation.

Single channel: there is no email/push provider in scope — the in-app inbox is the only delivery mechanism.

Integrity guard: if a create references an invalid source-record UUID (FK violation), that notification is skipped and warned — the log never points at a nonexistent record.

12 · Shared

Cross-cutting concerns

Rate limiting, caching, error normalization, and API documentation are shared infrastructure used by every module.

Rate limiting — Upstash-safe

Fixed window

Built on INCR + PEXPIRE (atomic, single-key) — no Lua EVAL, which Upstash doesn't support.

LimitValue

Auth endpoints5 req/min per IP
Login lockout5 attempts / 15 min per account

Caching

Index-set invalidation

Cache keys are tracked in a cache:index SET so invalidation uses SMEMBERS instead of the unsupported KEYS pattern. Writes remove affected keys before touching the DB, keeping reads eventually consistent.

Deployment facts

Migrations are applied non-interactively with npx prisma migrate deploy — the Supabase DB and the test DB both get the same 6 migrations.

Docker Compose starts only Postgres; Redis is not bundled because Upstash is the production store, and REDIS_URL is required (${REDIS_URL:?}).

RLS is enabled via migration; the app also validates every env var through Zod at boot and fails fast with a clear message.
